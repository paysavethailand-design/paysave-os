## 0. Executive decision and design guardrails

Engineering Blueprint v1.0 maps the frozen 21-domain, 161-table logical catalog into reviewable PostgreSQL physical contracts without creating executable implementation. Every physical choice is either frozen here as a design profile or explicitly benchmark/security/legal-gated. Any change to frozen ownership, tenant boundary, classification, retention, aggregate or dependency direction requires a new ADR.

**No-SQL evidence:** this artifact contains descriptive identifiers, type names and design matrices only. It contains no executable statement, schema creation, table creation, alteration, migration step or deployment command.

### Temporary assumptions requiring Gate confirmation

1. UUIDv7 is the preferred generated entity identifier; generator availability and monotonicity remain implementation evidence.
2. PostgreSQL native enum types are not used; controlled values resolve through versioned catalogs or bounded checks to avoid deployment coupling.
3. Encrypted business values use application-envelope encryption backed by managed KMS; exact algorithm/key provider is a Security Gate decision.
4. Required time-series partitions are physical targets; exact first/last boundary, future partition automation and child index templates are implementation evidence.
5. API and event sections define contracts only; they do not authorize handlers, endpoints, brokers or publication runtime.

### Physical key mapping rules

- Unpartitioned global tables: UUID entity identifier as physical primary identity.
- Unpartitioned tenant tables: UUID primary identity plus tenant candidate key `(partner_id, id)` for tenant-aware child references.
- Time-partitioned append tables: physical key includes the immutable partition timestamp plus UUID; no child may rely on UUID-only uniqueness of the partitioned parent.
- Entity-history hash partition: physical key and version uniqueness include the complete entity-identity partition key.
- Optional-global control-plane rows use explicit scope/owner columns; a null owner is permitted only where the frozen domain says global.

### Sensitive-column physical renaming

Logical PII names may map to `_encrypted` ciphertext and `_hash` lookup columns in the physical model. The Data Dictionary states each such rename explicitly. Precise latitude/longitude and customer/user display identity are never stored as plaintext; database-side geospatial or fuzzy-name search is prohibited unless a separately classified derived projection passes Security and Privacy review.

### Nullability and default rules

- `id`, tenant scope, immutable fact time, required parent references, currency paired with amount, and version/sequence fields are not nullable.
- A nullable FK is permitted only when the frozen logical catalog or ERD optional cardinality explicitly allows it; omission and unknown are not interchangeable.
- No business status, amount, classification, permission, consent, legal basis or approval result receives an implicit database default.
- Technical defaults may be proposed only for generated identity, UTC record time and an explicitly approved initial positive version; they remain Gate-reviewed physical decisions.
- Empty string is not a substitute for null. Whitespace normalization, case normalization and canonical code format are specified per contract.

## 12. Capacity Target

### Capacity bands

| Class |  Largest retained relation/object-manifest envelope | Physical planning response                                                                                            |
| ----- | --------------------------------------------------: | --------------------------------------------------------------------------------------------------------------------- |
| CP1   |                 below 1,000,000 active/control rows | non-partitioned by default; cache immutable published versions where useful                                           |
| CP2   |                  1,000,000 to below 10,000,000 rows | indexed/keyset access and monthly growth forecast                                                                     |
| CP3   |                      10,000,000 to 100,000,000 rows | benchmark partition alternatives, tenant-skew test, archive forecast and 30% free-capacity alert                      |
| CP4   | above 100,000,000 facts or high object/event volume | append-optimized path, lifecycle archive, object storage where applicable, per-partner skew and write-rate monitoring |

A row band is a design envelope, not a promise of measured throughput. For each relation, the Gate worksheet must calculate `annual rows = peak rows/day × 365 × safety factor`, `hot bytes = retained hot rows × measured row bytes`, and total capacity including indexes, WAL, temporary space, object metadata and archive manifests. These are formulas only; measured inputs are required before implementation acceptance.

| ----------- | ------------------------------------------------------------------------------------------- |
| Users       | more than 10,000 registered/active profiles in representative mix                           |
